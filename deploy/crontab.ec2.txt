#   neither of which exists on the server. If it was ever installed on EC2,
#   every job silently failed with "No such file or directory" — including
#   `ingest_settlement_reports`, which is what keeps the FBA actual-fee data

# INSTALL (on EC2):
#   crontab ~/Daily-Sales-Dashboard/deploy/crontab.ec2.txt
# VERIFY:
#   crontab -l
#   ls -l ~/Daily-Sales-Dashboard/logs/settlement.log
#
# Times are in the server's timezone (UTC unless changed). Adjust if the
# business wants these anchored to PST.
# ─────────────────────────────────────────────────────────────────────────────

# ── Management P&L ← Reports Repository (Date Range Transaction report) ─────
#   Posted-date basis incl. deferred, so a month is COMPLETE on the 1st. It
#   does not wait for settlement cycles (3rd-12th by marketplace) -- that is
#   the point of the source change. Runs on the 4th to leave Amazon room.
#
#   NOT self-sufficient: createReport is blocked for report type 1202, so the
#   monthly Transaction report must be GENERATED IN SELLER CENTRAL first. The
#   command says "no report yet" and writes nothing until it exists, which is
#   why the 5th-10th retries are here. Idempotent (delete-and-replace per
#   month), so the first success wins and later runs are free.
30 6 4 * *    cd $APP && $PYTHON $MANAGE sync_pnl_month --all-marketplaces >> $LOG/pnl.log 2>&1
30 6 5-10 * * cd $APP && $PYTHON $MANAGE sync_pnl_month --all-marketplaces >> $LOG/pnl.log 2>&1

# ── PPC / Ads ────────────────────────────────────────────────────────────────

# ── WALMART → AMAZON MCF AUTOMATION ──────────────────────────────────────────
# Import released Walmart orders + acknowledge (idempotent; PO id unique)
*/5 * * * * cd $APP && $PYTHON $MANAGE walmart_import_orders >> $LOG/walmart_mcf.log 2>&1

# Validate mapping + Blank-Box inventory, create MCF orders (BLANK_BOX + BLOCK_AMZL Required)
*/10 * * * * cd $APP && $PYTHON $MANAGE walmart_submit_mcf >> $LOG/walmart_mcf.log 2>&1

# Poll Amazon fulfillment status + harvest tracking numbers
*/15 * * * * cd $APP && $PYTHON $MANAGE walmart_check_status >> $LOG/walmart_mcf.log 2>&1

# Detect Walmart-side cancellations on pre-MCF orders (Walmart never pushes these)
5-59/15 * * * * cd $APP && $PYTHON $MANAGE walmart_sync_cancellations >> $LOG/walmart_mcf.log 2>&1

# Upload new tracking to Walmart (per-package dedupe; never re-uploads)
7-59/15 * * * * cd $APP && $PYTHON $MANAGE walmart_upload_tracking >> $LOG/walmart_mcf.log 2>&1

# Nightly reconcile: auto-complete finished orders, alert stuck/error ones
15 2 * * * cd $APP && $PYTHON $MANAGE walmart_reconcile >> $LOG/walmart_mcf.log 2>&1

# Backfill tracking for any manually-created MCF orders (transition safety net)
45 6 * * * cd $APP && $PYTHON $MANAGE walmart_backfill_tracking >> $LOG/walmart_mcf.log 2>&1

# Sync inventory from Amazon to Walmart (every 12 hours: 06:30 UTC + 18:30 UTC)
30 6,18 * * * cd $APP && $PYTHON $MANAGE walmart_sync_inventory >> $LOG/walmart_mcf.log 2>&1

*/30 * * * * cd $APP && for R in uk ae sa; do $PYTHON $MANAGE sync_today_ppc --marketplace $R; done >> $LOG/ppc_today.log 2>&1

# ── FBA Fee Intelligence → FbaFeeComponent (Data Kiosk economics) ────────────
# Rolling 10-day re-fetch across all marketplaces. Amazon's economics data
# settles over several days, so a single-day pull captures an incomplete
# picture and never revisits it. Re-reading a trailing window is self-healing,
# and safe to repeat: the parser dedupes on the table's unique tuple and
# bulk_create upserts, so running it twice gives the same answer as once.
# --all-marketplaces covers usa/uk/de/ae/sa and continues past a failure in any
# one region. Deliberately no date arithmetic: the BSD-vs-GNU `date` difference
# noted earlier in this file has already broken one job here.
0 7 * * *    cd $APP && $PYTHON $MANAGE ingest_fba_components --all-marketplaces --days 10 >> $LOG/fba_components.log 2>&1
